# البنية المعمارية — مهنة v2

## المبدأ

> المسار يوجّه، والخدمة تقرّر، والموديل يخزّن.

- **Routes** (`app/routes/`): قراءة الطلب، استدعاء خدمة، إرجاع رد. لا استعلامات معقّدة ولا
  منطق عمل.
- **Services** (`app/services/`): كل قواعد العمل + فحص الملكية + رفع الأخطاء (`DomainError`،
  `ValidationError`، `ForbiddenError`، `NotFoundError`). أي مسار جديد يحصل على نفس الحماية
  تلقائيًا.
- **Models** (`app/models/`): المخطط والعلاقات والخصائص الجاهزة للعرض
  (`Job.salary_label`, `Profile.completeness`, `Company.initials`).
- **Templates**: عرض فقط. لا استعلامات ولا حسابات أعمال.

## لماذا SSR + HTMX؟

- محركات البحث تحتاج HTML كاملًا (الوظائف هي المنتج).
- مستخدم 4G على هاتف متوسط لا يحتمل تحميل تطبيق SPA كامل لقراءة وظيفة.
- HTMX يعطي تفاعلًا (حفظ وظيفة، إشعارات، فلاتر) بدون بناء API منفصل ولا حالة مزدوجة.
- عند الحاجة لتطبيق موبايل لاحقًا: نفس الخدمات تُغلّف بـ JSON API في `routes/api.py`.

## تدفّق الطلب

```
Request → Blueprint route → Service (auth + validation) → SQLAlchemy → Template
                                   ↓ error
                        DomainError → flash + redirect (302)
```

الأخطاء المتوقّعة (صلاحية، ملكية، مدخلات) لا تُرجع 500 ولا صفحات خطأ مخيفة؛ تُرجع المستخدم
لمكان آمن مع رسالة عربية. أخطاء 401/403/404/429/500 لها قوالب موحّدة.

## النماذج الأساسية

| النموذج | ملاحظات |
|---|---|
| `AuthIdentity` | ربط هوية Google (`sub` المستقر) مع `User`؛ يمنع dopp accounts |
| `Profile` | مهارات/تعليم/لغات JSON + علاقات normalized (Skill/Language/Certification/WorkExperience/Education/PortfolioProject)، `completeness` محسوبة |
| `Company` | `owner_id` صريح (بدل حيلة v1)، حالة توثيق، `initials` |
| `Job` | `title_norm` + `search_blob` مفهرسة للبحث العربي، `status`، صلاحية |
| `Application` | فريدة (وظيفة + باحث)، حالات واضحة، سجل تغيير الحالة |
| `SavedJob` / `JobReport` / `Notification` / `AuditLog` | تفاعل، إشراف، إشعارات، تدقيق |

## البحث العربي

1. عند الإنشاء/التعديل: `Job.refresh_search_fields()` يطبّع العنوان والشركة والمدينة والوصف
   (إزالة التشكيل، توحيد الألف/الهمزة/التاء المربوطة/الياء، أرقام عربية → لاتينية).
2. عند البحث: نفس التطبيع + تقسيم لكلمات + مرادفات (سواق↔سائق، مطور↔مبرمج...).
3. OR داخل مجموعة المرادفات، AND بين الكلمات — نتيجة دقيقة بدون Elasticsearch.
4. لاحقًا: Meilisearch عند تجاوز ~50 ألف وظيفة (الواجهة لا تتغيّر).

## المصادقة

- **Flask-Login** بدل جلسات v1 اليدوية؛ `session_protection="strong"`.
- **Google Sign-In**: OAuth 2.0 + OIDC يدويًا في `services/google_auth.py` (بدون SDK):
  - `state` عشوائي في الجلسة + `secrets.compare_digest` (حماية CSRF للـ callback).
  - التحقق من `email_verified`، ورفض الحسابات المعطّلة.
  - ربط تلقائي بحساب موجود بنفس البريد، أو إنشاء حساب + ملف شخصي.
  - كلمة مرور عشوائية للحسابات المنشأة عبر Google (يمكن إعادة تعيينها لاحقًا).
- **حسابات التجربة**: `DEMO_ACCOUNTS` في الإعدادات، تُعرض كأزرار POST محمية بـ CSRF،
  وفارغة في الإنتاج.

## قاعدة البيانات والهجرات

- Alembic منذ اليوم الأول. لا `db.create_all()` في الإنتاج (كان في v1).
- الهجرة الأولى: المخطط الكامل. الثانية: `google_id` + `avatar_url`.
- SQLite محليًا، PostgreSQL في الإنتاج (`pool_pre_ping`).

## الاختبارات

- `TestingConfig`: SQLite في الذاكرة، CSRF وRate-limit معطّلان.
- تغطية: الصفحات العامة، التسجيل/الدخول، البحث والفلاتر، الصلاحيات (IDOR)، Google (state، ربط الحسابات، الحسابات المعطّلة).
- اختبارات الملفات الجديدة: `test_profiles.py` — CRUD الخصوصية، الوسائط، الرسائل، حساب الهدف.
- الاختبارات تؤكد **عدم تغيّر الحالة** عند محاولة غير مصرّح بها، لا مجرد رمز الرد.

## قرارات مقصودة

| القرار | السبب |
|---|---|
| لا SocketIO | v1 كان ينشئ غرفًا لا ينضم إليها أحد؛ HTMX polling أبسط وأصدق |
| `Company.owner_id` | يمنع «وظائف بلا مالك» ويسهّل فحص الصلاحية |
| POST-only للحذف/التغيير | يمنع تدمير البيانات عبر رابط أو prefetch |
| أرقام لاتينية + `<bdi>` | قراءة أوضح للرواتب والتواريخ في سياق RTL |
| seed عبر CLI فقط | لا بيانات وهمية تظهر في الإنتاج عند إعادة التشغيل |
